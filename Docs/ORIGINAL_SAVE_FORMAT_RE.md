# Original save format reverse engineering

## Status

This document describes the native Diggles `.sav` format used by the original executable. It is
the compatibility contract for the port's final save backend. The current implementation work is
in progress: the gzip container, archive primitives, header, top-level section pipeline, fixed
engine state, complete world-section boundaries, object declarations, support records, every
version `0xA5` generic object-body boundary, the current class table and spatial index, control
state through marker 8, control records through marker `0x50`, graphics state through marker 10,
and the complete version `0xA5` logic/action tail through marker 18 and physical end-of-stream are
verified. The implementation includes a lossless codec, typed terrain/fog/fluid and core object
documents, identity-first transactional preflight, an atomic filesystem repository, and DI
registration. Many late object, control, logic, and action fields still require semantic mapping
into the live runtime model.

The port's non-functional development `.dqs` JSON snapshot is retired. The final backend neither
reads nor writes it: original `.sav` is the only supported save format and compatibility target.

- length-prefixed string transfer: `FUN_004092c0` at `0x004092c0`;
- 98 original saves under `data/Gamesave`, all currently available fixtures at version `0xA5`.

The targeted instruction and caller dumps used for this analysis are generated by
`Tools/SaveFormatResearch/Ghidra/SaveFormatDump.java`.

## Container and primitive rules

The file is a standard gzip stream. The original writer clamps `GameSaveCompression` to `0..9`
and opens zlib in `wbN` mode. There is no port-specific wrapper outside the gzip payload.

The decompressed archive is packed without alignment padding. Primitive values are copied as raw
little-endian bytes from the 32-bit Windows process:

| Native helper | Encoding |
|---|---|
| `FUN_00409340` | one byte |
| `FUN_00598e40` | two bytes |
| `FUN_00406f60` | four bytes |
| `FUN_00408960` | eight bytes |
| `FUN_006bce60` | caller-supplied raw byte count |
| `FUN_004092c0` | signed `Int32` byte count including the terminating NUL, followed by that many bytes |

The archive object stores mode `1` for reading and `2` for writing. `FUN_006bce60` dispatches to
zlib read or write according to that mode. Its buffer and size are explicit at the instruction
level even where the decompiler omits the implicit `ECX`/`EDX` arguments.

## Version contract

The current writer always emits `0xA5` (`165`). The original loader accepts every version in the
inclusive range `0x86..0xA5`; other values are rejected before manager restoration.

Only `0xA5` fixtures are currently available. Older branches can be reconstructed from the loader,
but must remain version-gated and should not be described as fixture-verified until representative
saves are obtained.

Important gates in the main pipeline are:

| Condition | Format change |
|---|---|
| version `< 0x95` | legacy object payload is read before marker 5 |
| version `< 0xA1` | legacy class/object table is read before marker 6 |
| version `> 0xA0` | the same table family is read after the main dynamic-object graph |
| version `> 0x94` | the newer object payload is read before control state |
| version `> 0x99` | eight AI-owner states and planner state are present |
| version `> 0x9A` | an additional global value is present |
| version `> 0xA2` | a length-prefixed string and marker 18 are present |

## Verified archive prefix

The prefix is unaligned because the first string includes a single NUL byte in every available
fixture:

| Offset for current fixtures | Type | Meaning |
|---:|---|---|
| `0` | `Int32` | format version, currently `0xA5` |
| `4` | native string | header string; empty in all 98 available saves (`length=1`, then NUL) |
| `9` | `Double` | game time in seconds |
| `17` | `Int32` | section marker `1` |
| `21` | 205 packed bytes | fixed engine/application state |
| `226` | `Int32` | section marker `2` |
| `230` | `Int32` | section marker `3` |
| `234` | variable | world payload |

The game-time interpretation is supported by representative values of approximately `441.43`,
`57,326.65`, `68,710.44`, and `120,672.32` seconds and by the writer instruction that copies the
`Double` at global engine offset `+0xA088` immediately before marker 1.

### Section 1 fixed layout

`FUN_006b7710` writes exactly 205 bytes for version `0xA5`:

- three eight-byte values;
- three four-byte values;
- one byte;
- ten four-byte values;
- eight records containing four four-byte values each.

The semantic names of these engine fields are not yet established. Their size and marker boundary
are verified across all sampled saves.

Section 2 is empty in the current pipeline: markers 2 and 3 are adjacent.

## Top-level section pipeline

Markers are validation sentinels in a fixed serialization pipeline, not a directory with stored
lengths. Marker `0x50` is intentionally non-sequential.

| Marker starts after | Native serializer family | Loader progress group | Current interpretation |
|---:|---|---|---|
| `1` | `FUN_006b7710` | pre-world | fixed engine/application state |
| `2` | none in `0xA5` | pre-world | reserved/empty |
| `3` | `FUN_005931f0` | World | terrain blocks, fluid state, fog-of-war state |
| `4` | legacy-version branches | Objects | legacy object payload boundary |
| `5` | legacy-version branches | Objects | legacy class/object table boundary |
| `6` | `FUN_005d6790`, then `FUN_005b8d50` for current versions | Objects | dynamic object IDs, class names, object graph, class-specific state |
| `7` | `FUN_00592d70`, `FUN_00591fb0`, `FUN_005eeac0` | Control | newer object/control state |
| `8` | `FUN_00557b00` | Control | control records |
| `0x50` | boundary only | Graphics | transition from control to graphics |
| `9` | `FUN_00492250`, `FUN_00494300` | Graphics | graphics state after animation controllers |
| `10` | `FUN_005f8080`, `FUN_005fd670` | Logic | complete `CStoryMgr` payload |
| `11` | 81 calls to `FUN_0040b640` | Logic | nine numeric selection groups repeated nine times |
| `12` | `FUN_00406fe0` | Logic | variable logic collection |
| `13` | `FUN_005f4a70`, `FUN_005f4f10` | Logic | global two-value record collection |

| `18` | final tail | Logic | present only after version `0xA2` |

Every current save ends with a raw 4096-byte global block after the logic serializers. Its semantic
ownership is not yet named.

## Verified world payload for version `0xA5`

`FUN_005931f0` is sufficiently reconstructed to find marker 4 without scanning for marker-like byte
patterns. The payload is:

1. six `Int32` dimension/state values;
2. `width * height` packed terrain records, 53 bytes each;
3. eight four-byte fog/world values;
4. two additional four-byte global values;
5. fluid state from `FUN_0057ce70`;
6. eight fog-of-war sparse arrays;
7. marker `4`.

The six leading values are `width`, `height`, `minX`, `minY`, `maxXExclusive`,
and `maxYExclusive`. Late-campaign saves can have a nonzero `minY` (for example,
`512, 640, 0, 660, 512, 1300`). With full-width rows and `minX == 0`, the
archive stores the native ring buffer in storage order. Absolute tile `(x, y)`
is at `(y * width + x) % (width * height)`. See the native tile indexer
`FUN_00592f10` in [ORIGINAL_PATHFINDING_RE.md](ORIGINAL_PATHFINDING_RE.md).
The loader derives the terrain record count from the first two values.

### Terrain record

The current terrain record written by `FUN_00592f90` is 53 packed bytes:

| Archive offset | Native tile offset | Size | Meaning |
|---:|---:|---:|---|
| `0` | `+0x00` | 4 | BDB block index |
| `4` | `+0x06` | 1 | derived base navigation cost/validity |
| `5` | `+0x08` | 4 | eight owner dig-order nibbles |
| `9` | `+0x0C` | 4 | eight per-owner four-bit dig-order IDs |
| `13` | `+0x12` | 1 | floor flag and exit/crossing sub-cell |
| `14` | `+0x13` | 1 | template/dirty flags |
| `15` | `+0x14` | 2 | L2M cell ID |
| `17` | `+0x18` | 2 | material/dig precondition and adjacent terrain flags |
| `19` | `+0x1A` | 1 | fluid type for simulation buffer 0 |
| `20` | `+0x1B` | 1 | fluid type for simulation buffer 1 |
| `21` | `+0x1C` | 4 | fluid fill for simulation buffer 0 |
| `25` | `+0x20` | 4 | fluid fill for simulation buffer 1 |
| `29` | `+0x24` | 16 | fluid flow/cache values whose individual equations remain unnamed |
| `45` | `+0x34` | 8 | one persistent fog byte per player |

The native `+0x3C..+0x7B` 8 by 8 passability grid is deliberately not stored. It is re-derived
after load from the saved block/material state. Native cache fields at `+0x04`, `+0x10`, and `+0x16`
are reset rather than restored. This confirms that the save is a logical state archive, not a full
tile-structure memory dump.

The per-player dig-order counters are also not part of this payload. They belong to the separate
`DigMark` manager at `+0xB4[player]`: `FUN_005661c0:55-66` initializes all eight counters to zero,
the paint paths read their low nibble, and `FUN_00566550:124-131` / `FUN_00567cb0:229-236`
increment them after a committed order. `FUN_005931f0` serializes the tile nibbles but never the
manager counters. A newly constructed load session must therefore use the native transient default
of zero rather than infer a next value from the saved tile IDs.

### Fluid payload

The current fluid serializer contains:

- `Int32 sourceCount`, followed by `sourceCount` 37-byte fluid-source records;
- `Int32 stopperCount`, followed by `stopperCount` 41-byte fluid-stopper records;
- the current and previous simulation-buffer indices as two `Int32` values;
- two pairs of active/work-coordinate arrays, each encoded as `Int32 count` plus `count`
  `(tileX,tileY)` records;
- the `waterdbg` flag as one trailing byte.

A source record stores the owning object ID, cached three-float position, fluid type, four internal
rate/volume/height floats, and the vented flag. `SetFSource` proves the field mapping: `+0x14` is the
configured `-volume * 128`, `+0x18` is its remaining budget, `+0x1C` is the mutually exclusive
height target, and `+0x20` is `-vpf * 128`. The internal disabled sentinel is exactly `-1.0`; the
Tcl setter's no-update sentinel is `-10000`. A negative non-sentinel VPF remains an active drain.
Height values greater than or equal to one receive the native `+2` internal offset. A stopper
record stores the owning object ID, cached three-float position, dirty flag, integer
`{minX,minY,maxX,maxY}` bounds, and two directional permeability floats.

The four coordinate arrays are simulation work sets, not the liquid volume. Corpus saves often
contain liquid with every work set empty. Persistent type and fill live in the two per-tile buffers
at `+0x1A..+0x20`; the current/previous indices select between those buffers.

### Fog-of-war payload

Eight sparse arrays follow the fluid payload. Each array is `Int32 count` plus `count` `(tileX,
tileY)` pairs in one player's active fog-fade list. Together with the per-tile `+0x34..+0x3B`
bytes and the eight `fowBegin` rows stored before the fluid payload, these form the complete
persistent fog state.

## Dynamic object strategy

The object group is not a raw memory dump. It is a stable ID-based graph:

1. non-null object slots in the native `0x2000`-entry registry are emitted as an `Int32` object ID
   and a length-prefixed class name;
2. `-1` terminates the ID/class declaration list;
3. manager-side supporting records are emitted;
4. the same live IDs are emitted again, followed by `FUN_005d0ce0` generic and class-specific object
   state;
5. another `-1` terminates object bodies;
6. manager grids, references, and late object arrays follow.

Object references use registry IDs rather than process pointers. `FUN_00555d70` writes `-1` for a
null/invalid reference and otherwise writes the referenced object's registry ID. This makes native
graph reconstruction feasible in two passes: declare identities/classes first, then restore fields
and resolve references.

The typed document currently exposes each object's stable ID, class, native object type, position,
transient `+0x18..+0x20` position triple, inventory vector, ordered object strings, Tcl
variables, instance name, optional navigation-state presence, display state, player owner from native
`+0x36C`, and the adjacent common state groups through native `+0x2A4`. `FUN_005d0ce0` serializes the
pointer vector at native `+0x58` with its count at `+0x5C`; `FUN_005ce010`, `FUN_005ce930`, and the
Tcl `inv_add` path prove this is the native inventory. All inventory targets resolve inside the
declared identity set. Corpus audit found 39 extra multi-owner occurrences, 29 inventory entries
whose target no longer has the native `contained` bit, and no containment cycles. These are accepted
original-game states, so the port retains every ordered inventory entry and derives its single
`ContainedIn` convenience field only for a bit-marked target, choosing the first ID-ordered owner
when a stale duplicate cannot be represented uniquely. This is the first identity-first mapper
boundary: objects can be allocated by ID before inventory, attachment, action, or Tcl references are
resolved. Owner values are validated as `-1` (unowned) or a player index in `0..7`; they are not
object-registry references.

The raw link value at native `+0x278` is serialized as an ordinary `Int32`, not through the guarded
object-reference serializer. Current fixtures contain 27 dangling positive values (for example
object 1978 linking to absent value 1972), so preflight preserves this value but does not require it
to resolve. The live mapper resolves valid attachment parents only after all identities exist and
maps an absent parent to the port's null link instead of retaining a dangerous dangling handle.

### Current object manifest and support records

For version `0xA5`, markers 4, 5, and 6 are adjacent. The declaration stream starts immediately
after marker 6. Its `-1` terminator is followed by an empty native string and then an `Int32`
support-record count. The support count is not constrained by the 8192-slot object registry;
`save_test.sav` contains 9,143 records.

Each support record contains a 28-byte prefix followed by the payload serialized by
`FUN_005b9f00`:

- a fixed 32-byte class/resource name;
- four object references;
- nine four-byte values;
- two native strings;
- three four-byte values;
- one eight-byte value.

The first body ID follows the final support record. Body IDs occur in the same strictly increasing
order as declarations and end with `-1`.

### Verified version `0xA5` generic object body

`FUN_005d0ce0` starts every body with the class name again and an `Int32` object type. The common
payload then serializes transforms, general state, child references, string arrays, 16 fixed
values, Tcl variables, an object reference and state string, route state, an optional 512-value
grid, navigation state, display data, ownership/control fields, and two later 16-entry state groups.

The common payload contains four explicitly tagged optional groups:

- an `Int32` presence value for the 512-value grid;
- a byte presence value for a 160-value navigation block;
- a byte presence value for attachment-history records;
- a byte presence value for an action variant (`0`, `1`, or `2`).

Object-type-dependent extensions are deterministic after the type is read:

| Object type | Additional payload |
|---:|---|
| `1`, `11` | three actor-link records, a string array, and one flag |
| `1` | named-index stream, dwarf-specific four-value state, and other actor state |
| `5`, `6`, `7`, `10` | mobile/building work-state block |

The body tail contains an optional late action variant, a 64-slot support table with per-slot
presence bytes, a variable support-record array, one four-byte value, and one final byte. Type `-1`
is valid and occurs on spectator-style objects; observed current types span `-1..12`.

The object bodies are followed by manager-owned arrays, a current-version action-record array, the
class table, and a map-sized spatial index. The action-record count is zero in all 98 available
fixtures. Its non-empty class-specific variants therefore remain instruction-derived but not
fixture-verified. The spatial-index bucket count is deterministic:

`ceil(world width / 8) * ceil(world height / 8)`

Each bucket stores a count followed by that many fixed-prefix, class-named spatial records. Marker
7 immediately follows the final bucket.

`Tools/SaveFormatResearch/parse_a5_object_bodies.py` implements the instruction-level boundary
probe. It has validated all 98 available original saves without scanning for marker-like patterns:

- 146,151 object bodies;
- 245,798 support records;
- 112,821 class-table entries;
- 122,046 spatial records;
- zero declaration/body ID mismatches;
- zero calculated body-boundary mismatches;
- zero calculated marker 7 mismatches.

The production `OriginalSaveArchiveReader` performs the same bounded validation and exposes
declaration, class histogram, support count, body type, offset, size, class-table count,
spatial-index counts, and marker 7 offset metadata without mutating the live world. Focused Unity
EditMode tests cover representative tutorial and large-world saves as well as malformed version
and marker rejection.

## Verified control payload for version `0xA5`

The payload after marker 7 is the native class-light manager from `FUN_00592d70`/
`FUN_00591fb0`. Its sparse table has 2048 slots of 36 bytes each. Every serialized entry consists
of an ordered slot index in `0..2047`, position XYZ as exact float words, three native 0..31 color
channels, radius as an exact float word, a source token, and the exact trailing class-light value.
The serialized final two words correspond to in-memory slot words 8 and 7 respectively because of
their historical version gates. Index `-1` terminates the table, and marker 8 follows immediately.
`FUN_00591480` allocates these per-object light slots and `FUN_00591a20` updates them while dirtying
native lighting. A source token greater than one is the owning stable object ID. Tokens 0/1 belong
to static map-light instances created without a dynamic object owner.

The current 103-save configured corpus contains 26,897 active slots, with maximum used slot 779.
There are 18,134 object-bound entries; every source ID resolves, and no save binds the same object
twice. `Misc_Light` owns 17,622 of them, while production buildings, chests and scripted light
sources account for the remainder. The other 7,111/1,652 entries use static source token 0/1. All
positions, radii and trailing values are finite; observed radii are 1, approximately 1.2, 2, 3, 4,
4.5, 5, 6 and 8, and observed trailing values are -1, 0 and 356.

The production reader exposes a bounded typed document for the complete table. Transactional
preflight validates finite positive numeric state, 5-bit colors, source-token semantics, dynamic
object identities and unique per-object bindings. Immutable staging retains every exact raw word.
The port still rebuilds live presentation lights from object/class data, so exact manager
continuation and static-light presentation remain activation blockers.

The payload after marker 8 is native `EnergyMgr` state serialized by `FUN_00557b00`. It contains:

1. an `Int32` control-record count;
2. for each source, its stable object reference, energy class, and exact range float bits;
3. a nested lease count followed by stable consumer object reference, exact charged-amount float
   bits, and remaining 10 Hz ticks for each lease;
4. marker `0x50`.

The boundary probe validates all 98 current fixtures through marker `0x50` without scanning:

- 27,076 sparse control-state entries;
- 185 control records;
- 6 nested control records;
- zero calculated marker 8 or marker `0x50` mismatches.

The called `FUN_005eeac0` initializes derived state while loading but writes no archive bytes in
writer mode. It therefore does not add an undocumented payload between the sparse table and marker
8.

The production typed document preserves source order and exact range/amount bits. Preflight
validates unique source IDs, all source/consumer identities, and finite numeric state. Immutable
staging restores the complete table into the inactive candidate after entity shell creation without
running Tcl. In the current 103-save configured corpus there are 183 source records and five active
leases. Source classes are `Laufrad` (99), `Dampfmaschine` (53), and `Reaktor` (31), with native
energy classes/ranges `1/20`, `2/60`, and `3/100` respectively. Saved lease countdowns are 4615,
4635, 5630, 5641, and 5815 ticks.

## Verified graphics payload for version `0xA5`

The payload after marker `0x50` begins with the sparse `CAnimCtrl` table serialized by
`FUN_00461e20`/`FUN_004620e0`. Each entry uses an ordered controller index in `0..8191` and contains
one raw byte, one exact eight-byte animation-time/state value, a declared value count, a current/
compatibility value, an `Int32` value vector, and five trailing four-byte values. The first trailing
value repeats the outer controller index exactly. The next two contain animation-control state and
may retain native allocator fill. The fourth is a model-database slot in `-1..255`; loading it also
rebuilds the derived model pointer, which is deliberately not serialized. The final word is the
animation ID/state. ID `-1` terminates the table, immediately followed by marker 9.

The controller index is not always a dynamic object ID. Every declared dynamic object has a
controller entry in the current corpus, but static map/render instances occupy additional indices.
Therefore an unmatched controller index is valid graphics state rather than a dangling object
reference. The raw byte and several control words also contain widespread `0xDF` allocator residue
and must be retained rather than interpreted as booleans or rejected.

The production reader now exposes a bounded typed document through exact marker 9. Transactional
preflight validates the finite 64-bit value, declared/vector count equality, repeated-index
invariant and native model-slot range while accepting raw allocator residue and static indices.
Immutable staging deep-copies all 613,909 records and their value vectors in the current corpus.
The port does not yet map these records onto live `DigglesAnimator` instances, so frame/time/
animation continuation remains an activation blocker.

The second graphics table is the native particle manager serialized by `FUN_00494300`. Its
4096-slot records are 0x88 bytes in memory and are allocated/freed by `FUN_00495070`/
`FUN_004957e0`; construction and restoration use `FUN_00495940`. Each active entry serializes its
ordered slot index, particle kind, particle count, position XYZ and direction/delta XYZ as exact
float words, the exact word at record offset `0x50`, the byte at `0x64`, the exact word at `0x60`,
mode at `0x5C`, and the version-gated words at `0x68`, `0x70`, `0x74`, and `0x80`. Index `-1`
terminates the table, immediately followed by marker 10. The native Tcl seams
`CreateParticleSource`, `SetParticleSource`, `ChangeParticleSource`, and `FreeParticleSource`
confirm that these are persistent particle sources rather than a generic render table.

An instruction-aligned probe over the current 103-save configured corpus found 32,559 active
particle records and maximum slot 4095, with no duplicate or out-of-order slots and no non-finite
serialized float. Counts span 0..309, the byte at `0x64` is exactly 0/1, and mode values are
0/1/5/6. The `0x70` word is `-1` for 32,541 records, static token 0 for 12 records, and stable object
ID 6740 for six records; all six dynamic references resolve in their save. The `0x74` word is
always -1 in this corpus, while `0x80` contains 0/1/3. Fields without instruction-level semantics
remain raw even where the current corpus has a narrow distribution.

The production reader exposes the complete table as a bounded typed compatibility document.
Transactional preflight validates nonnegative particle counts, finite float-backed fields, the
native 0/1 byte, and dynamic object links before staging. Immutable staging preserves every exact
word. The port does not yet apply this table to a session-aware live particle presenter, so exact
particle continuation remains an activation blocker.

The version-`0xA5` common `CObj` body also contains the per-object half of particle persistence.
The byte previously labelled as navigation-state presence is actually the `obj+0x2B0` particle
state gate in `FUN_005d0ce0`. When present, `FUN_005da020` serializes exactly 160 `Int32` words:
32 global particle-manager handles, 32 relative-position XYZ vectors, and 32 raw link-ID words.
`FUN_005d86f0` allocates a source handle, `FUN_005d8930` writes its relative position, and
`FUN_005d8990` writes the optional model-link ID. The link array is not initialized by every native
creation path and therefore legitimately contains allocator residue; it must remain raw.

Across the current 103-save corpus, 24,027 objects carry this block and expose 28,887 nonnegative
attachments through source index 15. There are 23 stale handles not present in the saved global
particle table, 1,276 duplicate handle attachments, and 4,965 global particle records not attached
through an object block. These are native compatibility cases rather than parser errors: the
global manager also owns temporary/static sources, while object arrays can retain stale/shared
slots. All relative positions are finite. The typed document and immutable runtime snapshot retain
the complete block; preflight validates only finite positions and the proven `-1..4095` handle
domain.

All 98 current fixtures validate through marker 10 without scanning:

- 619,875 animation controllers;
- 1,480,250 animation-controller vector values;
- 32,882 graphics entries;
- zero calculated marker 9 or marker 10 mismatches.

## Verified early logic and action payload for version `0xA5`

The first logic manager after marker 10 is the complete `CStoryMgr` serialized by `FUN_005fd670`.
Its version `0xA5` payload is:

1. a counted event array; each event contains name, trigger class, extra trigger argument and a
   completion byte;
2. a counted array of 100-byte native unique-template records, serialized as name, two native
   indices, placed byte, counted event-index vector, depth range, exact float word and referenced
   template index, native dimensions, dig-connect value, group index, exclusive byte, origin,
   zone/zone-border indices, placed position, alignment byte, stone index and two exact float words;
3. a counted template-group array; each group contains its name, counted child records
   (`name, x, y, width, height, completed`), three header values, counted four-value connection
   records and counted five-value material rectangles;
4. selected-template string, one unstable native word, result rect, scan cursor and raw free rect;
5. a counted string-pair record array, then counted flat story-map values and exact dimensions;
6. counted named zone upper bounds, callback script/object reference, zone floor, latch state and
   dig-pressure/message/threshold state.

The three group header values are native width, height and the first `-digconnect` argument. The
per-template dig-connect word is its second argument. Group child records reproduce the
`CampaignInit.tcl` child X/Y plus referenced template dimensions. Five-value material records use
native corner form `{x0, y0, x1, y1, type}`; the port converts them back to Tcl extent form only for
its inactive runtime candidate and retains the native words separately.

Across all 103 currently available saves, the manager is either the valid empty constructor state
or contains 59..65 events, 27 unique templates, 23 groups, a 128 by 160 map and four zones. All
current template event-index vectors and string-pair arrays are empty. The word after the selected
template string is not a reliable identity: observed values include `-1`, valid-looking indices,
zero, native debug fill `0xDFDFDFDF` and another garbage-like word. It is therefore preserved
opaquely and never used to resolve an object or template.

The production reader exposes a bounded typed document for this entire payload. Transactional
preflight validates all template/event/group/zone and callback object references, finite numeric
values, dimensions, counters, latch direction and exact marker-11 termination. Runtime staging
clones the state immutably and reconstructs the inactive candidate's story registries without
running campaign Tcl or invoking callbacks. Marker 11 follows this manager. The next section
contains nine numeric selection/control-group `Int32` vectors. Due to a native writer bug, the save
loop reloads `CGame + 0xA0EC` on every outer iteration and writes the same nine vectors nine times,
for 81 serialized vectors total. The loader overwrites the same nine runtime vectors with each copy.
All 98 files in the primary fixture corpus and all 103 configured Unity fixtures contain identical
copies. Live values are stable object registry IDs; every one of the 232 members in the configured
corpus resolves to a `Zwerg`, and no canonical group contains duplicates.

The semantics are instruction-verified. The input handler reads Ctrl from input offset `+0x11B`:
Ctrl+1..9 copies the current selection into the selected vector, while plain 1..9 copies that vector
back to the active selection and recenters when it was already selected. `FUN_00535D70` scans the
same vectors to append the numeric group annotation in the selection UI. The production document
retains all 81 vectors, transactional preflight rejects a divergent repeated copy or dangling/
duplicate member, and runtime staging exposes the canonical nine groups. Marker 12 follows the last
repeated vector.

The action manager after marker 12 serializes one record per participating object:

1. an object registry ID;
2. an action type in `0..11`;
3. the type-specific `CAct_*` payload;
4. object ID `-1` as the table terminator;
5. sentinel `0x626C6133`;
6. an auxiliary record vector, whose nested records contain eight four-byte values each;
7. sentinel `0x626C6134`;
8. marker 13.

The shared current action state is not fixed-width: it contains three Tcl strings encoded through

## Verified late logic tail and end of payload for version `0xA5`

The remaining current-version pipeline is:

1. after marker 13, the counted native sparetime/leisure-place registry, then marker 14. Each
   record is exactly `(category, objectRegistryId)`. `FUN_005f4ee0` maps the case-insensitive Tcl
   names to `sleep=0`, `eat=1`, `bath=2`, `fun=3`, `home=4`, `sex=5`, and `ill=6`.
   `sparetime announce` updates an existing record by its second word or appends a new record;
   `disannounce` removes it. Query walkers resolve the object ID on demand and skip missing
   objects, so a stale ID is valid compatibility state rather than an archive-integrity failure;
2. the native `TriggerService` sparse slot array, then marker 15. Each slot begins with the raw
   serialized pointer value used as a presence token. Zero is an empty slot. A nonzero slot contains,
   in order: serialized record index, trigger kind, execution mode, owner object ID, fire-script
   native string,
   `LastCheck`, `CheckTimer`, `CheckIdle`, `CheckNear`, one-byte active flag, raw float target range,
   `FireTime`, interval, target object ID, target-class native string, target-type bit mask,
   target-owner-spec native string, target count, callback-script native string, and actuator-list
   native string. The pointer value is process-specific opaque data and must not be interpreted as a
   stable ID. The original loader reads the record index as ordinary state and does not compare it
   with the enclosing slot. The fixture corpus includes at least one live slot whose saved record
   index is `-1`, so equality with the slot number is not a valid archive invariant;
3. the counted horizon/fog-region registry from `CGame + 0x2868/+0x286C`, then marker 16. Each
   record is 32 bytes:
   `(positionX, positionY, positionZ, redByte, greenByte, blueByte, depth, size)`.
   `TCL:CTclGlobalMethods::HorizonSet` removes the first existing record whose XY distance from
   the new position is less than one native unit, rounds/clamps `r/g/b * 255`, then appends the new
   record. `HorizonRem` applies the same XY removal law and `HorizonClear` empties the vector;
4. the counted adaptive-sound marker registry from `FUN_004d1090`/`FUN_004d18f0`, then marker 17.
   Each current-version record contains a stable object ID or `-1`, position X/Y/Z as raw floats,
   one exact NUL-terminated native theme string, and a range float. Versions above `0x8A` contain
   the range word. `adaptive_sound marker` creates a positional `-1` record; `markerobj` creates an
   object-bound record with initial zero position and range 50. The manager uses actual XY distance
   and the saved range when choosing a positional marker. All 248 records in the current 103-save
   corpus are positional, so stale object-bound reference behavior is not fixture-proven;
5. the `ViWinNewsTicker` state from `FUN_00519230` when the invariant global object is present:
   a counted active-record array, counted retained-history array, category mask, and counted
   display queue. Active records contain an exact native text string, packed color, raw category
   word, two text metrics, priority/effective-priority/remaining-time float words, notification ID,
   two presentation bytes, exact click-script string, timestamp double and history byte. History
   records contain text, packed color, click script, raw category word and ID. Queue records contain
   ID and raw float position. The category word is native allocator residue unless Tcl supplied
   `-category`: 32/48 active and 1,682/3,785 history records in the current 103-save corpus are
   outside the semantic 0..5 range. They must be preserved rather than rejected; the port runtime
   safely maps them to the command default `fight`. All 48 saved queue IDs resolve to current active
   records. The native next-ID member is not serialized and must be derived collision-free;
6. the fixed 128-slot native object-icon table serialized by `FUN_004c4370`. Each slot is an object
   reference followed by value, opaque runtime word, icon type and XYZ offset raw-float words. The
   manager allocator `FUN_004c1640` initializes `{object,type,value,opaque=-1,offset}`; known live
   types cover hitpoints (0), other status overlays (1/2), production progress (3) and named class/
   work icons (5). The current 103-save corpus contains 2,018 active slots, all resolving to declared
   objects and all retaining opaque `-1`; observed types are 0, 1, 2 and 5;
7. the counted `CMapBeautifier +0x30` cave-rectangle vector serialized by `FUN_0058ecd0`. Each record
   is exactly `{x0,y0,x1,y1,size}`. The current corpus contains 131 ordered records, all with ordered
   bounds inside the saved native world and size/template selector 0..3. This table drives cave
   completion and is gameplay continuation state, not disposable presentation;
8. eight AI-owner states, each containing an enabled byte, an owner value, script name, and Tcl
   variable dictionary. For current `0xA5`, every owner slot is exactly: one-byte enabled flag,
   owner index, native script-path string, Int32 Tcl-interpreter presence, and, when present, a
   counted sequence of native variable-name/value string pairs. The original loader sources the
   saved script before applying the saved variable dictionary when the enabled flag is set;
9. the 78-byte `CElf` singleton state from `FUN_00429100`, including two particle-source handles
   gated by version `> 0xA3`. The 17 four-byte words map to texture variant, current/requested
   registered animation, model database/mesh IDs, frame alpha, look-at object, position, two lean
   values, a currently zero `+0x64` compatibility word, target and movement mode; two bytes are
   draw-over-UI and animation-continuation flags;
10. 32 reserved archive-framing values followed by eight native player-session records. Each player
    record contains two native strings, slot state, player/clan owner IDs and an eight-value diplomacy
    row;
11. marker 18, gated by version `> 0xA2`;
12. a final 4096-byte write-only zero-padding block from `DAT_00ca4460`, followed immediately by
    physical end of the decompressed stream. Native writer `FUN_00557170` emits it unconditionally,
    but native loader `FUN_00556570` does not consume it at all. The address lies in zero-filled
    virtual `.data` storage beyond the executable section's raw bytes, and all 103 current saves
    contain exactly 4096 zero bytes. It is therefore not RNG or restorable simulation state.

Every available version `0xA5` save contains the global object needed for step 5. The original
writer makes that call conditional, so a future document model must preserve the condition from
the object graph rather than assuming the block exists for every theoretically valid archive.

The dedicated typed news-ticker corpus test over the current 103-save directory observes

## Port compatibility architecture

The final backend should use five layers:

1. Native reader/writer codecs validate gzip, version, primitive bounds, strings, markers, and
   collection limits without mutating the live world.
2. A version-aware native document model stores terrain, objects, references, script/control state,
   AI, and presentation-independent logic.
3. A mapper constructs or updates the Unity/Tcl runtime in identity-first order, then resolves
   references and restarts actions at a safe native boundary.
4. `OriginalSaveLoadPreparationService` is the first application-service boundary. It orchestrates
   archive loading, complete preflight validation, and immutable runtime staging without touching
   the live Unity/Tcl graph. It and its dependencies are registered through the project's DI
   composition root. The final save/load service will add the transactional live commit, atomic
   file updates, and user-facing results; UI and input code will depend only on that service
   interface.
5. `OriginalSaveArchiveWriter` emits the same versioned document model. The retired `.dqs` format
   has no adapter and is not allowed to define or influence the native schema.

`OriginalSaveCurrentArchiveWriter` now proves the first writer boundary for version `0xA5`: it
serializes the typed common prefix of every object body, preserves each still-opaque class-specific
tail verbatim, copies the remaining native sections, then runs the complete structural reader over
the rebuilt payload. The tutorial fixture rebuild is byte-identical. This is intentionally not yet
the live-runtime writer: object-tail and global manager fields must be mapped before gameplay saves
can safely replace their source values.

The writer also accepts a validated semantic patch for variable-length common state. The current
coverage includes game time, object position/velocity/rotation, work window, generic reference
vector, ordered Tcl variables, state reference, instance/display names, owner, fog reveal state,
link state, placement mode, object/dirty flags, and dig-order ID. Rebuilding a tutorial object with
shorter vectors and longer strings passes the full reader and load preflight. This proves that body
and downstream section offsets are derived from serialization rather than copied absolute values;
it does not relax the requirement to map every remaining field before exposing gameplay save.

The same writer can now rebuild the complete variable-length world section. A typed world patch
updates terrain blocks, per-owner dig state, both fluid buffers, fluid sources/stoppers and work
sets, fog bytes, fog rows, and all eight fade lists while preserving still-unnamed tile cache words.
An empty world patch reproduces the tutorial payload byte-for-byte; a patch that changes both fluid
and fog collection lengths reparses through physical EOF and passes transactional load preflight.

`OriginalSaveRuntimePatchMapper` is the first live-capture adapter. At a safe Tcl/simulation
boundary it maps identity-stable runtime entities back to the verified native fields above. It
rejects non-finite state, invalid owners or links, class changes, and any added or removed entity
before a payload can be built. The graph restriction is deliberate: declaration/class tables and
class-specific object tails are not yet writable, so silently dropping a runtime entity would make
the save appear valid while losing gameplay state. The backend remains unavailable to players
until that restriction and the remaining subsystem mappings are removed.

When the live terrain and fog services are present, the mapper also captures block/material and
per-owner dig changes, persistent fog/fade state, fluid cells, source budgets/rates, and directional
stoppers. The port has one authoritative fluid cell state rather than the original tick's two
transient buffers, so capture writes the same type/fill into both buffers and emits empty work sets;
the original rebuilds those sets during simulation. Missing terrain or fog is rejected instead of
silently producing a partial world archive.

`OriginalSaveRuntimeArchiveService` composes that mapper with the typed writer and atomic
repository. Its contract has no UI, input, gzip, or filesystem-policy leakage: it captures at the
safe boundary, rebuilds and fully revalidates the native payload, then atomically replaces the
destination. A real-file integration test reads the captured `.sav` back through the repository.
The service is registered in the VContainer composition root but is not assigned to the Tcl
`IGameSaveBackend` while graph mutation and complete live load remain unsupported.

The typed AI owner section is also mapped into the immutable runtime snapshot. Transactional
preflight currently supports only the exact shipped `data/scripts/ai/std_ai.tcl` policy observed in
all 103 saves and rejects inconsistent interpreter flags or duplicate globals. Candidate restoration
does not execute the save-provided path. `AiSystem` sources its hard-coded trusted policy inside the
inactive session, recreates the tick handler and owner scope, overlays the saved Tcl variables, then
restores the enabled flag and derives the staggered next tick from saved game time. The tutorial
candidate test proves all native globals and enabled/interpreter state are restored without running
object `obj_init`; full AI continuation remains gated by the other manager/story/RNG activation
blockers.

`FUN_00429100` was previously mislabeled as planner persistence. Cross-references to
`DAT_0076a274`, `FUN_00427610` and the 200 Hz `FUN_00427e30` tick prove it is the tutorial narrator
`CElf`. The port now has a bounded typed document and immutable snapshot for the exact 78-byte
state. Across all 103 saves the model database is 254, mode is 0, current/requested registered
animation are both 0, `+0x64` is zero, and every nonnegative native mesh ID resolves to an exact
`standanim` frame in `elfe.3db`. The high 4081..4090 values are particle-manager handles, not world
object IDs. Candidate staging restores every serialized field, resolves the current model frame,
and infers visibility from native mesh presence without invoking Tcl; particle presentation is
recreated by `ElfPresenter` rather than treating those native handles as ordinary entities.

`FUN_00557c70` serializes the eight native player-session records at `game + 0xA424`, with a 0x34-byte
stride. Constructor `FUN_0055a060` initializes each name to `Nobody`, player/clan IDs to the slot,
the secondary name to empty, and diplomacy to neutral 3 with own diagonal 0. Across all 103 current
saves those identities and strings remain exact; diplomacy additionally contains enemy value 4.
The preceding 32 values written by `FUN_00557bf0` have no state pointer and are archive framing, not
zero padding: 23 corpus values are one. The typed document therefore preserves all 32 losslessly.
Candidate staging restores the complete player table and diplomacy matrix before AI state, without
executing Tcl or mutating the active session.

Reader limits must reject negative or excessive string and collection lengths before allocation.
Loading must be transactional: a malformed or unsupported archive must not partially destroy the
current world. Saving must write to a temporary file and replace the destination only after the
complete archive has been successfully finalized. The codec, mapper, and orchestration service must
remain separately testable; service lookup and scene-wide singleton discovery are not part of the
design.
