# Hat (Muetze) & Object Link / Attachment-Point System

Reverse-engineered (Tcl scripts + decompile + empirical dump of
`data/3db/mann.3db`). This drives rendering hats, and — using the same mechanism —
items/weapons/tools held in the hands, glasses, hair, crowns, etc.

> Verified against the code:
> `DigglesLinkPoints`, `DigglesLinkAttachment`, `DigglesAnimator.TryGetLinkOffset`/
> `TryGetLinkRotation`, and `DigglesAnimController.SetAlternate` (§5.4) all present;
> the crown helpers are gone as §5 states. Implementation matches this doc.

> **Status: ✅ IMPLEMENTED & VERIFIED IN PLAY.** Dwarf hats (both genders) render,
> seat on the head, track the animation (move/turn/tilt), and the put-on sequence is clean. The
> final seating approach IS the faithful "pin hat origin at link-4" — an earlier crown-centroid
> detour was an over-correction and has been removed (see §5). Sections 1–3 are faithful RE; §4
> documents the link binary format; §5 documents what was built (and the dead ends).

## 1. Worn hats are `Dummy_Muetze_*` classes

The worn hat is NOT the `Zipfelmuetze` class (that's the floating death-cap dropped on
death). Worn hats are `Dummy_*` render-only classes auto-generated by `SetDummyClassesAll`
(`init/animinit.tcl ~259-348`) from the table in `classes/items/muetzen.tcl:3-53`; each
becomes class `Dummy_<name>` with default anim `<model>.standard` (a still).

There are MANY hats — chosen by `get_nameofmuetze_proc` (`classes/zwerg/z_work_common.tcl:780-832`):
- gender suffix: male → `a`, female → `b`.
- clan (`clanname`, `""` = human): non-human clan OR `sparetime` category → `Dummy_<clan>Muetze_<a/b>`.
- occupation category → `Dummy_Muetze_<stein|holz|metall|nahrung|energiemagie|dienstleistung|arbeitslos>_<a/b>`;
  `fight` → `Muetze_kampf_01/02/03_<a/b>` by `exp_Kampf` tier.

Default idle hat for a human dwarf: `Dummy_Muetze_a` (male, model `muetze_a`) / `_b` (female).

## 2. Create / attach / remove (`classes/zwerg/z_work_common.tcl`)

```tcl
proc create_muetze {muetze_name} { #:767-778
    del_current_muetze
    set m_ref [new $muetze_name]
    set current_muetze_ref  $m_ref
    set current_muetze_name $muetze_name
    link_obj $m_ref this 4                    # attach to head link-point (index 4)
    set_visibility $m_ref 1
    set_textureanimation $m_ref 0 $hatcolor 0 0   # tint to player color
}
proc del_current_muetze {} { #:722-737
    set_visibility $current_muetze_ref 0
    link_obj $current_muetze_ref              # 1-arg = UNLINK
    del $current_muetze_ref
}
```

State vars (`zwerg.tcl obj_init:11`): `current_muetze_name`/`current_muetze_ref` (`0`=none),
`muetzen_counter` (debounce). Methods are thin wrappers: `z_methods.tcl:154-185`.

**Put-on animation** (what the player observed at spawn): `prod_change_muetze` → `muetze_auf`
(`z_work_common.tcl:740-761`) queues a tasklist `play_anim hatongone; hatonhand; hatonhead;
create_muetze`. Anim→clip names (`z_anims.tcl:226-233`): `hatonhead`=`mann.hut_auf_kopf`,
`hatonhand`=`mann.hut_auf_hand`, `hatongone`=`mann.hut_auf_weg`, wall=`mann.wand_muetze_auf`.
Triggered from `sparetime_dispatch` state_enter (`z_spare_main.tcl:5-15`) when the current hat
≠ the wanted hat. A minimum-viable path can skip the animation and `create_muetze` directly
(`muetze_auf` has a "noanim" path).

## 3. The link / attachment system (engine)

- `link_obj <child> <parent> <linkid>` — attach child to parent at link point `linkid`.
  `link_obj <child>` (1 arg) — detach. (decompile `FUN_0069b7b0`; parent stored on child
  `+0x278/+0x27c` via `FUN_005cb700`.)
- `get_linkpos <obj> <idx>` — returns the link point's offset rotated by the object's
  orientation; scripts use `vector_add [get_pos $obj] [get_linkpos $obj $idx]` for world pos.
  `get_linkrot` returns its orientation. (decompile `FUN_00686d10`.)

Dwarf "mann" link-point indices (0..31): **0 = right hand** (weapon/held item), **1 = left
hand** (shield), **4 = head** (hats, hair, glasses, crown, helmet, diving bell), **6/11 = body**
(particle emitters), **7 = carry hand** (tools), **10 = mouth** (potions, face fx).

## 4. Link-point binary format & per-frame indexing (EXACT)

Link points are baked markers in each morph keyframe (the models are vertex-morph, no
skeleton), so attachments ride the animation perfectly. To compute a link point's
**model-local** offset for `(animIndex, frame, linkId)`:

```
meshIndex = model.Anims[animIndex].Indices[frame] // anim frame → morph mesh keyframe
slot = uint32_at(model.Meshes[meshIndex].Block128, linkId*4) // 32-slot link table
if (slot >= model.Triangles.Length) → no link (treat as origin)
rec = model.Triangles[slot].Raw // 20-byte record; first 3 u16 = quant xyz
x = (u16_at(rec,0) / 4 - 8192) * 0.005
y = (u16_at(rec,2) / 4 - 8192) * 0.005
z = (u16_at(rec,4) / 4 - 8192) * 0.010 // NOTE: Z scale is double X/Y
// → model-local offset. Engine then rotates by the entity orientation and adds get_pos.
```

Our `ThreeDbParser` already captures everything (names are misleading):
- `model.Triangles[]` = the engine's global 20-byte link/vertex pool (NOT triangles; real
  triangles are `model.IndexLists`). count = the `u32` after the list-count `u16`s.
- `model.Meshes[i].Block128` = the 128-byte (32 × u32) link table at mesh byte `+0x5c`.
- `model.Anims[i].Indices` = the frame → mesh-keyframe-index array.

Dequant constants (from `Diggles.exe`): `(u16 | 0x43800000)*8192 - 2105344` ≡ `u16/4 - 8192`;
world scale `DAT_00736fcc = 0.005` (X/Y), `DAT_00736fe0 = 0.01` (Z). Decompile: `FUN_00686d10`
(GetLinkPos), `FUN_00408920` (×0x14 record indexer), `FUN_00408a10` (dequant), `FUN_00402640:38`
(mesh +0x5c 32×u32 table), mesh stride `0xE8` (`C3DDB_Persist`).

**Empirical check (`mann.3db`):** 11573 mesh keyframes, 1023 anims, 62543 link/vertex records.
Standing `stand_anim_a` frame 0: head(4) local `(-0.004,-0.998,0.048)`, rhand(0) `(-0.193,-0.104,
-0.095)`, lhand(1) `(0.258,-0.020,0.103)`, mouth(10) `(0.000,-0.638,0.608)`. Model is **Y-DOWN**
(top = most-negative Y), so head Y=-0.998 sits high — consistent. `schlafen` frame 0 head differs
→ per-frame confirmed.

**Object → anim → mesh resolution (CORRECTED):** in the `.3db`, `object.Indices` are ANIM ids,
and `anim.frames` are MESH ids. The hat resolves as `object muetze_a → obj.Indices=[2] →
anim[2]="standard" → frames=[23,24] → meshes 23/24` (a small cap). `DigglesModelLibrary.FindAnim`
searches the object's OWN anim list for the clip name → correct. (51 distinct objects each define
their own anim named "standard" → its own mesh pair; `muetze_b`→25/26, etc.)

**Vertex vs link scale (CORRECTED — they differ):** the engine uses a UNIFORM model scale for
mesh VERTICES (`FUN_0048ba80` "CModelRenderer Vertexprocessing", all axes equal — doubling vertex
Z visibly distorts the body, confirmed). LINK records are a SEPARATE path that scales X,Y×0.005 but
Z×0.010 (`FUN_005f5ef0`/`FUN_00686d10`, the `fVar+fVar` Z-double, `DAT_00736fe0`). Our port decodes
vertices uniformly (correct) and the inner model applies `Q_x(-90)` + a uniform `ModelToWorldScale`
(0.005). The link-Z×2 turned out NOT to be the thing that fixes the hat (see §5) — what matters is
WHERE on the head the hat seats, not the raw link offset.

## 5. Implementation in the Unity port (as built,)

The plumbing (link_obj/get_linkpos, per-frame link offset+rotation, the attachment component)
works as the RE says. The **final** head-seat is the faithful one: pin the hat origin at the raw
link-4 point (per-frame, interpolated) with the per-frame link-4 rotation. Getting there took a
wrong turn through a "crown" approach that has since been removed.

### 5.1 The crown detour, and why the raw link point is actually correct
The engine pins the child's raw model origin at the parent link point with NO child-side offset
(`FUN_005f5ef0`; child stores only parentid `+0x278` / linkid `+0x27c` via `FUN_005cb700`). The
hat mesh is authored to **extend forward+down over the skull from that point**, so origin-at-link-4
covers the head correctly — link-4 is right as-is.

Earlier we misread an up-and-behind hat as "link-4 is the back apex, the mass bulges forward" and
moved the seat to the **head-crown centroid** (centroid of head-submesh top-band verts). The crown
sits **~21 model-units FORWARD of link-4** (the hair-top is ahead of the skull apex) — so seating
there **double-counts** the mesh's own forward reach and shoves the hat onto the face. This only
became obvious once the gnomes animated actively (gender/clothing/AI all live) and the hat was
clearly mis-seated on everyone. **Proof it's link-4:** the player's manual model nudge that fixed it,
`(0, -11.8, -20.7)`, applied to the measured crown→link-4 offset `(-0.4, 13.3, 22.2)`, lands back
on `(0, 1.5, 1.5) ≈ link-4`. So the crown was removed; head links now use the raw link point like
every other link.

Dead ends along the way (all removed):
- **Doubling vertex-Z** (to match the link-Z×0.01): distorts every body. Wrong — vertices are uniform.
- **A fixed seat offset rotated by the link rotation** (absolute or delta): swings the hat sideways,
  because the link Euler (which correctly *orients* the hat) is NOT the head's geometric rotation.
- **Crown centroid** (per-frame top-Y band): three sub-bugs chased in turn — hand-pollution (fixed by
  head-submesh restriction), per-clip wobble, and topology mismatch
  + tilted-frame index pick (fixed by `(model, vertexCount)` keying + a `standard` rest-pose source).
  Each fix made the crown *consistent*, but it was consistently in the **wrong place** (too far forward).
  The real lesson: don't synthesize a seat — use the link point the engine already provides.

### 5.2 The working design — raw link point
- **Position** = the per-frame, f0→f1-interpolated link-4 offset (`DigglesAnimator.TryGetLinkOffset`).
- **Orientation** = the per-frame link-4 rotation (`TryGetLinkRotation`) — makes the hat turn/tilt
  with the head. (This part of the RE was always correct.)
- Head links and hand/item links (0/1/7/…) are now treated identically: raw link offset + rotation.

### 5.3 Code
- `DigglesModelLibrary` — clip build populates `SourceModel` + `SourceMeshIndices` + the per-frame
  vertex-decode affine (`FrameLinkA/S`) for link lookup; correct bbox vertex decode.
- `DigglesLinkPoints.TryGetLocalOffset/Euler` — §4 link decode (offset + Euler from the 20-byte rec).
- `DigglesAnimator` — `TryGetLinkOffset`/`TryGetLinkRotation` (per-frame, interpolated). (The crown
  helpers `TryGetHeadCrownCentroid`/`CrownPerFrame`/`CrownIndicesFor` were removed.)
- `DigglesLinkAttachment` (on the child) — `Place` each LateUpdate: every link → raw link offset +
  rotation. `DigglesTclEngine.CmdLinkObj` wires `link_obj`/detach and parents the child under the
  parent's inner "Model" node.
- Flow: `loadRealClasses` on → Tcl `create_muetze` → `new Dummy_Muetze_*` spawns via the runtime
  spawner (model from the class default anim) → `link_obj $ref this 4` attaches it.

### 5.4 Gender / clothing / frau model (this same commit)
The hat *variant* and the dwarf *model* are gender-driven (see also Docs/FACE_ANIMATION.md):
- `auto_choose_gender` balances population, `set_objgender`/`get_objgender` store the male/female bit,
  `obj_query -class/-owner/-flagpos` filters actors. Female → hat suffix `b`, male → `a` (§1).
- A female dwarf calls `set_alternateanimdb true` → the controller re-skins it to the **`frau`** model
  (`DigglesAnimController.SetAlternate`): it remaps `mann`→`frau` for ALL clips, bare AND `mann.`-prefixed
  (`SplitObjAnim`), so a prefixed anim like `mann.hut_auf_kopf` can't revert the model to male.
- On that swap, `DigglesTextureAnimator.ClearChannels` drops stale `ZMann_` variant textures so they
  don't paint onto the new frau mesh; clothing/hair/face re-resolve `ZFrau_` fresh.
